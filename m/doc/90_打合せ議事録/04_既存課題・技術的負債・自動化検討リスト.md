## 1. メダップのサービス特性と改善の基本方針

* **強みと課題のジレンマ**：
  * 他社の医療SaaSが行わない「手作業でのデータクレンジング」や「マスタとの丁寧な突合」を行っている点がメダップの競争優位（強み）である一方、その運用負荷やデータ不整合がチャーンレート（解約率）に影響を与えている側面もある。
* **基本方針**：
  * ユーザー（病院側）にマスタ管理を任せることはサービスの提供価値を大きく損なうため現実的ではない。
  * **「重複データは発生する前提」** に立ち、不具合や運用負荷を減らす仕組みづくりを目指していく。

## 2. 課題①：重複医療機関データの統合（126件）

### 現状と発生メカニズム
* **現状の件数**：Asanaで管理されているチケット上、同じ医療機関が別番号（別ID）で登録されてしまっている重複医療機関が **126件** 存在する。
* **発生原因**：
  1. 医療機関マスタ（MIS）は厚生労働省の公開データをもとに月1回更新しているが、新規開業したクリニック等が公式マスタに反映・審査されるまでにはタイムラグが生じる。
  2. そのタイムラグの間に、**foro CRM** 上で「紹介元・紹介先となる新規クリニックをいち早く登録しておきたい」というニーズが発生し、手動で登録が行われる。
  3. 結果として、後から取り込まれる公式マスタのデータと手動登録データが二重に存在してしまう。

### 統合処理におけるリスクと技術的難易度
* **誤統合のリスク**：本来は別の医療機関であるものを誤って1つに統合してしまうリスクを避けるため、慎重なデータ名寄せ（確認作業）が必要となる。
* **DBテーブル統合の複雑さ**：
  * 重複する医療機関IDに紐づくテーブルは **20〜30個** に及ぶ。
  * 単純な `UPDATE` 処理だけでは統合できないテーブルが存在するため、手作業や慎重な判断が求められる。
  * *(※DB定義補足：`foro` DBの `crm_medical_institution_phases` や `mis` DBの `medical_institution_specialties`、`ref_naviis` 等、`medicalInstitutionId` を含むユニーク制約が存在するテーブルが多いため、単純なID付け替えでは制約違反やデータ競合が発生する)*

### 自動化・効率化に向けた技術的見解（Kyohei Yoshida）
* **同一施設の判定 vs 統合処理の切り分け**：
  * 「どの病院とどの病院が同一であるか」の判断自体は自動化が難しい。
  * 一方で、判断後の **データ統合処理（DB更新等）自体はバッチ化や半自動化の余地がある**。
* **重複データの自動検知**：
  * 現在はData Opsチームのメンバーが毎月のデータ登録・クレンジング作業の中で手動で重複を発見し、Asanaに蓄積している。
  * **MCPやAIツール** を活用すれば、Asanaにアクセスして重複データを自動的に検知・抽出する仕組みを構築することは理論上可能である。

## 3. 課題②：介護施設データの重複・未自動化問題

### 重複問題の構造と影響
* **原因**：介護データは保険種別ごとに施設タイプが細分化（110〜780番台まで存在）されており、1つの施設が7件ほどの届出を持つケースがある。
* **影響**：重複登録されると **foro CRM** 上でデータが分散し、訪問履歴やコミュニケーション実績をどのレコードに紐づけるべきか曖昧になり、集計カウントも正しく行えなくなる。
* **医科・歯科との違い**：
  * 医科・歯科の重複は全体約15万〜16万件に対して千件程度（大病院の一部）であり、「医科側に寄せる」ルールで解決できた。
  * 一方、介護施設は届出ごとに名称が微妙に異なり検索のかかり方も変わるため統合が難しい。

### 現状のステータスと優先度
* 1施設に複数タイプを持たせるデータ構造の変更までは実施したが、**重複レコードの統合自体は未対応**。
* CSやセールスからは優先度が高いと要望がある一方、柳内氏の判断で開発優先度が低く置かれており、黒川氏の退職までに対応完了するのは厳しい状況。
* また、介護サービス情報公表システムのデータ自体、半年に1回（6月分が7月、12月分が1月2日）公開されるが、**定期更新が未自動化**のままである。

## 4. 課題③：定例作業・マスタ登録の自動化における壁と打ち手

### 厚生局マスタ登録の自動化難度
* 厚生労働省（厚生局）のホームページから公開データを取得し、正規化・マスタ（MIS）登録を行う一連の作業は、現状すべて手作業で実施している。
* 原本データが正規化されていないことや、名称変更・閉院新規開院・移転など個別のケースごとに「人の判断」が介在するポイントが多いため、完全な自動化が難しい状況にある。

### 逆紹介リスト（外来適正化）作成プロセスの自動化アイデア
* **現状の課題**：毎月のデータ催促、Google Driveからのコピー、YAML書き換えとPython実行、およびCSからの顧客ファイル送付まで一連の手作業が発生している。
* **前提**：今月・来月（11月・12月）はまず手作業で流れを完全に理解した上で自動化へ着手する。病院側はITリテラシーの制約上、Boxへファイルをアップロードするのが精一杯という前提で設計する。
* **自動化案（山田氏提案・合意）**：
  * 毎月 **25日** などに **GAS（Google Apps Script）** や自動化基盤を定期実行し、「Google Driveからのファイル確認・取得 → YAML書き換え → Pythonスクリプト実行 → 完了結果をSlackの指定チャンネル／ディレクトリへ通知」までを自動化する。
  * 引き継ぎのたびにマニュアルを作り直す非効率をなくすため、**「マニュアル自体をプログラム化する」** 方針で合意。

## 5. 課題④：DB構造ドキュメント（ER図・CRUD表）の不足と整備方針

* **課題**：
  * 現状、システム全体のER図やCRUD表が不足している。
  * `referrals` と `referral_masters` のようなDB間・テーブル間の論理的な関連性にも物理制約（FK等）がなく、属人的なノウハウとして残っている。
* **整備方針（吉田氏提案・山田氏依頼）**：
  * 改修時の予期せぬ影響範囲を防ぐため、リバースエンジニアリングや既存資料・コードからの逆算（ボトムアップ）＋AI活用によって、DB構造やCRUDの骨組みが分かる資料を安全に再構築・蓄積していく。
  * 山田氏からも過去AIで生成を試みて断念した経緯が共有され、吉田氏へ資料作成を正式に依頼した。

## 6. 課題⑤：システム上の技術的負債・運用リスク

| 項目 | 現状と課題・リスク |
| :--- | :--- |
| **完了通知の二重システム** | データ投入完了後、①プロダクト画面上のステータス更新（`data_importing_logs` 等）と、②毎朝7時に Cloud Tasks 経由で配信する完了通知メールの2系統が並行稼働している。黒川氏も「統合すべきだった技術的負債」と認識している。 |
| **`data-management-api` の独立構成** | Pythonチームでの運用を想定して別APIとして切り出したが、体制が実現しなかったため、他システムから独立して浮いている状態になっている。 |
| **誤データ・古いデータの混入リスク** | 投入前の手動確認と異常値検知（月平均から30%以上乖離でアラート）を設けているが、すり抜けるケースがあり、1年以上前の古いデータが紛れ込んでも誰も気づかないことが稀に発生する。 |
