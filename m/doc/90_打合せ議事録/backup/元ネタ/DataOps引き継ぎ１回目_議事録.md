## 3. Data Ops の全体像と基盤構成

### Data Ops の役割と対象データ
* **役割**：顧客（病院）の既存システムから出力されたデータおよびオープンデータをクレンジング・整形し、データベースへ投入する仕組み。
* **対象外**：**foro CRM** 上でユーザーが直接画面入力するデータはData Opsの対象外。

### 全体のデータフロー
1. 病院の電子カルテやExcel等からエクスポートされたデータ（紹介・逆紹介データ、DPCデータ〔様式1/FF1等〕）を **Box** にアップロード。
2. **`data-integration`** 経由でタスク管理・ファイル連携を実施。
3. **`medup-core-service` の管理API（`apps/api`）** 側でクレンジング・整形を実施。
4. 本番の **AlloyDB（PostgreSQL互換）** およびアナリティクス基盤（BigQuery等）へ格納。

### 関連API・分析基盤の構成
* **`data-management-api`（Python / FastAPI）**：
  * 名寄せや一部のデータ整形処理を切り出した別API。
  * 元々はPythonを使う専門チームで運用する想定で切り出したが、そのような体制にならなかったため、現状は独立して飛び出ている構成となっている。
* **BI・分析ツール（主にCSがデータ閲覧に利用）**：
  * **Redash**：元々は本番の **AlloyDB** を直接参照していたが、現在は **Datastream** でレプリケーションした **BigQuery** を優先して参照する方針に変更されている（現状は両方へ接続可能）。
  * **Tableau**：外来適正化（逆紹介）の領域でのみ使用している。

## 4. オープンデータの取り込みと課題

### 扱うオープンデータの3種別

| データ種別 | 取得・更新方法 | 定期取り込み | 備考 |
| :--- | :--- | :---: | :--- |
| **厚生局の医科・歯科指定データ** | 月次公開。Data Ops担当が手動で取得・一部加工し、管理ツール（`admin-web`）からインポートして **MIS** 本番を更新。 | あり（手動＋ツール） | — |
| **ナビイ（navii / 医療情報ネット）** | Excel/CSVでの公開形式がないため**スクレイピング**で取得。`data-management-api` 等のスクレイピング機能が**毎週金曜日**に自動実行しDBへ反映。 | あり（自動） | *(※社内ナレッジ補足：`tmp_ref_naviis` 経由で `ref_naviis` へ反映)* |
| **介護サービス情報公表システムデータ** | 当初は定期更新を想定しておらず**未自動化**。 | なし | 半年に1回（6月分が7月、12月分が1月2日）公開されるため、本来は更新が必要という認識。 |

### 未解決の課題：介護施設データの重複問題
* **原因**：介護データは保険種別ごとに施設タイプが細分化（110〜780番台まで存在）されており、1つの施設が7件ほどの届出を持つケースがある。
* **影響**：重複登録されると **foro CRM** 上でデータが分散し、訪問履歴やコミュニケーション実績をどのレコードに紐づけるべきか曖昧になり、集計カウントも正しく行えなくなる。
* **医科・歯科との違い**：
  * 医科・歯科の重複は全体約15万〜16万件に対して千件程度（大病院の一部）であり、「医科側に寄せる」ルールで解決できた。
  * 一方、介護施設は届出ごとに名称が微妙に異なり検索のかかり方も変わるため統合が難しい。
* **現状とステータス**：
  * 1施設に複数タイプを持たせるデータ構造の変更までは実施したが、**重複レコードの統合自体は未対応**。
  * CSやセールスからは優先度が高いと要望がある一方、柳内氏の判断で開発優先度が低く置かれており、黒川氏の退職までに対応完了するのは厳しい状況。

## 5. ユーザーデータ受領〜Asana起票・通知の自動処理フロー

### ① アップロード時の自動連携（Box → Google Drive / Slack / MongoDB）
1. ユーザーが **Box** の「ユーザーからCSへ」ディレクトリにファイルをアップロードする。
2. Webhook をトリガーに **`data-integration`** が起動し、以下の3処理を実行する。
   * **Google Drive** へのファイルコピー（作業用保管）
   * **Slack** への通知
   * **MongoDB** への「未対応データレコード」作成
* **Google Driveへコピーする理由**：Box上のままだと、ユーザーによるファイル編集でWebhookが再発火したり、勝手に移動・削除されたりするリスクがあるため。

### ② テナントフォルダのマッピング管理
* CSがBox上にテナント別フォルダを作成すると、WebhookをトリガーにGoogle Drive側にも自動で対応フォルダが作成される。
* アップロード時はMongoDB内のマッピングレコードを参照してコピー先を判定し、Asanaのカスタムフィールド（テナントマッピングオブジェクト）を利用してAPIエラーを防ぎながら連携している。

### ③ 未対応データの振り分けとAsana起票
* アップロードされたファイルには作業不要なデータも含まれるため、一度MongoDBに未対応レコードとして蓄積する。
* Data Ops担当者が毎朝、内製ツール上で未対応レコードを確認して「対応要否・ファイル種別」を振り分けると、以下の処理が実行される。
  * MongoDBから未対応レコードを削除
  * Google Drive内のファイルを `Inbox` から `受領データ` フォルダへ移動
  * **Asana** に作業チケットを自動起票

### ④ データ投入完了後の通知（二重システム・技術的負債）
データ投入が完了すると、以下の2系統の仕組みが並行して動いている（黒川氏としては統合すべきだった負債と認識）。
1. **画面上のステータス更新**：プロダクト上でユーザーが月別のデータ受領・投入状況を確認できる画面（`data_importing_logs` 等）が更新される。
2. **完了通知メール配信**：古くからの要望で残っている仕組み。毎朝7時に **Cloud Tasks** のトリガーでコアAPIからチケット情報を取得し、データ投入完了メールをユーザーへ配信する。

## 6. 紹介データの取り込み・名寄せ（クレンジング）とDB構造

### 前提：匿名化・仮名化と患者番号の統一
* 紹介・逆紹介データは、DPCデータ（外部提出用）と異なり院外へ出す想定がないため、病院側で匿名化・仮名化されずにエクスポートされるケースが多い。
* 一方、foro CRM上で「紹介」と「入院」を紐付けて分析するためには全データ間で患者番号を揃える必要があり、顧客や抽出方法によって加工の有無が異なる前提で運用している。

### クレンジング・名寄せの作業プロセス
1. **受領データのチェック**：紹介作業シートの作成時に、元データとの件数一致および事前のすり合わせ通りのカラム構成であるかを確認。
2. **自動マッピングと作業シート出力**：MISの医療機関レコードとの名寄せは、過去に蓄積したマッピング（`medical_institution_mappings`）で自動処理し、**新規の表記ゆれ（未一致）のみ**作業シートに出力する。
3. **ブラインド作業による確定**：派遣・契約社員約5名のData Opsメンバーが、シートごとに **2名体制でブラインド作業** を行い、両者の判定に差分があれば最終確認（レビュー）で確定させる。
4. **取り込み後チェック**：DB投入後に、投入件数および入院データとの紐付け件数を確認する。

### 誤データの再取り込み（洗い替え）と異常値検知
* **洗い替え対応**：ユーザーから提供されたデータに誤りがあった場合は、該当ファイル単位で管理画面の削除ボタンから本番データを削除し、正しいデータを入れ直す（洗い替え方式）。
* **手動確認と安全策**：
  * 本番データへ直接影響するため、投入前に必ず人が確認する（同月データの重複有無や、CS経由の再送連絡などを手がかりにする）。
  * 1年以上前の古いデータが紛れ込んでも気づかないケースが稀に発生する。
  * **異常値検知**：月平均から **30%以上乖離** した場合にアラートを出す仕組みを導入しているが、すり抜けるケースもあるため、あくまでセーフティネット（安全策）の位置づけ。

### 保存先の二重構造（`referral_masters` と `referrals`）と整合性維持
作業完了後の紹介データは、以下の2つのテーブルに保存される（逆紹介も `reverse_referral_masters` / `reverse_referrals` で同様の構造）。

| テーブル名 | 所属DB | 役割・保持内容 |
| :--- | :--- | :--- |
| **`referral_masters`** | `data_ops` DB | **親データ（原本表記の保持）**。ユーザーの元表記や対応関係を保持し、調査時に遡れるようにしている。（元々スプレッドシートで管理していた作業をDB移行した経緯がある） |
| **`referrals`** | `foro` DB | **本番業務データ**。`referral_masters` からコピーされ、ID化されたデータが格納される。 |

* **紐付けキー**：両テーブルは **`tenant_id`** と **`referral_control_id`** によって **1対1** に対応付けられている（`referral_masters` 側で `[tenant_id, referral_control_id]` のユニーク制約あり）。
* **修正・問い合わせ対応時の重要注意点**：
  * 片側のテーブルだけを手動修正すると、後で差分が発生して調査が混乱する（再取り込み時にも不整合が起きる）ため、**必ず両テーブルを合わせて修正する**必要がある。
  * 「紹介数がゼロになっている」などの問い合わせを受けた際は、ユーザー画面から遡って件数差分とマッピングを確認し、**実データ（DB）と蓄積マッピング（`medical_institution_mappings`）の両方を修正**する。

### 診療科マッピングの運用
* 診療科は病院内の部署名にあたり、組織再編で年度ごとに表記が変わる上、誤るとユーザーからの反発が大きい。
* そのため医療機関名のような作業シートは使わず、管理ツール（`admin-web`）のテナントマスタ管理にある「診療科」タブ（`own_department_mappings` 等）で個別に確認しながら手作業で登録・編集している。
