# GCPシステム運用におけるデプロイ・設定変更およびトラブルシューティング標準作業手順書

## 1. マニュアルの目的と適用範囲

本標準作業手順書（SOP）は、GCP（Google Cloud Platform）基盤上で稼働するWebアプリケーション群のデプロイメント、環境設定変更、トラブルシューティング、および本番トラフィック切り替え運用を標準化・構造化するために作成されています。

本手順を正しく遵守することにより、本番環境における障害発生リスクの極小化、リリース作業時の人的ミスの排除、デプロイリードタイムの短縮、および継続的デリバリーにおけるシステム安定性の維持を実現します。

### システム構成と主要コンポーネントの分析

本手順書が対象とするシステム環境は、**Cloud Build**（CI/CD）、**Secret Manager**（環境変数・シークレット管理）、および **Cloud Run**（コンテナ実行基盤）で構成されています。インフラ構成上の重要ポイントとして、対象サービスは目的ごとに複数のGCPプロジェクト（`Analytics` プロジェクトおよび `medup-flow-prod` プロジェクト）に分断して配置されています。

GCP Console操作時に適切なプロジェクトを選択しない場合、対象リソースが発見できず誤操作やリリース遅延の原因となるため、下表の定義に基づいて構成と手動介入領域を正しく把握してください。

| コンポーネント / サービス名 | 役割 / 種別 | 対象GCPプロジェクト | 自動化領域 | 手動介入が必要な領域 |
| --- | --- | --- | --- | --- |
| **Cloud Build** | CI/CD パイプライン | `medup-flow-prod`<br>`Analytics` | GitHub PRマージ時のビルド自動キック | ビルド異常停止・ハング時の手動再実行（Re-trigger） |
| **Secret Manager** | 環境変数・フィーチャーフラグ管理 | `medup-flow-prod`<br>`Analytics` | アプリケーションからの動的シークレット参照 | 新規バージョン（ペイロード）の追加作成および反映用ビルド起動 |
| `follow-crm-api-prod` | Cloud Run (本番API) | `Analytics` | コンテナイメージのビルドおよびレジストリ保管 | 新リビジョンの確認および本番トラフィック（100%）手動切替 |
| `follow-crm-api-worker-prod` | Cloud Run (本番ワーカー) | `Analytics` | コンテナイメージのビルドおよびレジストリ保管 | 新リビジョンの確認および本番トラフィック（100%）手動切替 |
| `follow-crm-spa-prod` | Cloud Run (本番フロントエンド) | `Analytics` | コンテナイメージのビルドおよびレジストリ保管 | 新リビジョンの確認および本番トラフィック（100%）手動切替 |
| `careflow-web-production` | Cloud Run / Webアプリケーション | `medup-flow-prod` | マージ時のコンテナビルド実行 | シークレット更新後の手動ビルド再実行（Re-trigger）またはPRマージ連携 |

### 作業前準備・事前要件の定義

作業担当者は、作業開始前に以下のアクセス権限および運用要件が完全に満たされていることを確認してください。

- **GCP Console アクセス権限:** 対象のIAMアカウントで Google Cloud Console にログインできること。
- **マルチプロジェクト権限の所持:**
    - `Analytics` プロジェクトにおける Cloud Build 実行権限、Cloud Run トラフィック管理権限。
    - `medup-flow-prod` プロジェクトにおける Secret Manager 閲覧・作成権限および Cloud Build 実行権限。
- **プロジェクト切り替えの意識:** コンソール上部のプロジェクトセレクターで、操作対象サービスが存在する正しいGCPプロジェクトが選択されているかを作業の都度確認すること。
- **GitHubリリース状態の把握:** リリース対象となるプルリクエスト（PR）の差分、マージ状態、およびビルド対象ブランチ（`develop` や `main`/`master`）が正確に把握されていること。

作業前準備の完了後、まずCI/CDパイプライン上で発生するビルド異常の検知と手動リカバリー手順について解説する次セクションへ進みます。

## 2. Cloud Build デプロイトラブルシューティング手順

CI/CDパイプラインにおいてビルド異常を早期に検知し、迅速に対処することは、障害コードの本番混入を防ぎ、サービスの継続的デリバリーとシステム全体の安定性を維持するために不可欠です。本セクションでは、ビルドのハングアップ現象の特定手順と手動リカバリー（Re-trigger）フローを定義します。

### ビルドハング・失敗事象の分析

Next.js 等のビルド工程において、静的ページ生成段階（`Generating static pages`）で処理が完全に停止し、そのまま約58分間（約1時間）ハングアップした後に異常終了（タイムアウト）となる障害パターンが確認されています。

正常時のビルド完了時間は **10分弱（約7〜8分）** であり、50分以上経過しても完了しない場合はプロセスがハング状態にあると判断し、手動での介入および再実行が必要です。

### Cloud Build 履歴・ログ確認手順

1. **GCP Console でのプロジェクト切り替えとナビゲーション:**
    - コンソール上部のプロジェクトセレクターで、対象のGCPプロジェクト（例: `Analytics` または `medup-flow-prod`）を選択します。
    - 検索バーに「Cloud Build」と入力し、「Cloud Build」の画面に移動します。
2. **履歴（History）での対象トリガー検索:**
    - 左側ナビゲーションメニューから「履歴（History）」タブをクリックします。
    - 画面上で `Command + F`（または `Ctrl + F`）を使用し、対象のトリガー名（例: Webステージングビルド等）を検索します。
3. **実行時間の比較評価:**
    - 同一トリガーの過去の成功履歴を確認し、正常時の実行時間（約10分弱）に対し、対象のビルドが50分以上経過して止まっていないか実行時間を比較・評価します。
4. **アクティブなログ確認:**
    - ビルドのハッシュID（コミットハッシュまたはビルドIDのリンク）をクリックしてログ詳細画面を開きます。
    - ログの最下部までスクロールし、`Generating static pages` 等の特定の出力箇所でログ出力が停止していることを確認します。

```
[Cloud Build ログ確認イメージ]
...
info  - Creating an optimized production build
info  - Compiled successfully
info  - Collecting page data
info  - Generating static pages (40/40)  <-- ここで約58分間停止・ハングアップ
```

### 手動再実行（Re-trigger）のステップバイステップ手順

1. 左側ナビゲーションメニューから「トリガー（Triggers）」タブに移動します。
2. 対象のトリガー名（例: ステージング環境用Webビルドトリガー等）を一覧から特定します。
3. トリガー行の右端にある「実行（Run）」ボタンを押下します。
4. ブランチ選択ダイアログにおいて、指定のデフォルトブランチ（例: `develop` ブランチ等）が選択されていることを確認し、手動実行を確定します。

### 未解決時の安全策・判断基準の提示

手動再実行（Re-trigger）を行っても再度同一ログ（`Generating static pages`）で停止・ハングが再現する場合、以下の安全プロトコルに従ってください。

- **本番無影響の確認:** Cloud Run 等の本番トラフィック切替操作を実施していない限り、本番環境では旧バージョンのコンテナリビジョンが継続稼働しています。ソースコードがリポジトリに取り込まれていても、トラフィックを切り替えない限りユーザー環境へ影響は及びません。
- **作業中断と調査エスカレーション:** 同一のログでハングが継続する場合は本日のリリース作業を一旦中断してください。該当コードの依存ライブラリ、静的ページ生成ロジック、あるいはビルド環境のリソース枯渇について開発チームおよびインフラリードへ調査を依頼・エスカレーションしてください。

次セクションでは、コードを変更せずに安全に機能を有効化する Secret Manager の設定変更および環境同期手順について説明します。

## 3. Secret Managerによるフィーチャーフラグ設定および環境同期手順

フィーチャーフラグ（Feature Flag）管理は、アプリケーションコードを再デプロイすることなく、機能の有効化・無効化や画面要素の動作を動的に制御するための重要な運用手法です。本手順では、Secret Manager を用いた Staging 環境と Production 環境の設定同期手順を解説します。

### ステージング・本番環境の差分評価とフィーチャーフラグの実態

事前に Staging と Production のシークレット内容を比較・検証します。今回のリリースサイクルにおいては、以下の2つのフィーチャーフラグが対象となります。これらはプログラムコード自体は過去のデプロイで既に反映済みですが、フラグ値が OFF に保持されていたため本番未有効化の状態にありました。

1. `入院調整`**（Hospitalization Adjustment）機能フラグ**
2. `医療機関・紹介元の表示順変更・ドラッグ＆ドロップ` **機能フラグ**

**差分検証手順:**

1. GCP Console で対象プロジェクト（`medup-flow-prod`）を選択し、「Secret Manager」を開きます。
2. Staging 用と Production 用のシークレット（例: `careflow-web` 関連シークレット）をそれぞれ別タブで開きます。
3. 最新バージョンの操作メニュー（点々アイコン）から「値の確認 / シークレット表示」を選択し、設定されているテキスト（環境変数・フラグ一覧）を表示して Staging と Production の差分を比較します。

### Secret Manager のバージョン更新手順

Secret Manager のペロードは不変（Immutable）構造となっており、**既存のバージョンを直接編集することは不可能です**。設定変更時は必ず新しいバージョンを追加します。

1. **既存ペイロードの全コピー:**
    - 既存の最新バージョンの「値の確認 / シークレット表示」を開き、表示されたテキスト全体をコピーします。
2. **新規バージョンの追加作成:**
    - シークレット詳細画面上部の「新しいバージョンを追加（Add new version）」をクリックします。
3. **フィーチャーフラグの追加・更新:**
    - 貼り付けた既存ペイロードの末尾に、今回有効化するフィーチャーフラグ行を追加・更新します。

```
[Secret Manager ペイロード設定更新例]
EXISTING_ENV_VAR_1=value1
EXISTING_ENV_VAR_2=value2
FEATURE_FLAG_HOSPITALIZATION_ADJUSTMENT=true
FEATURE_FLAG_MEDICAL_INSTITUTION_ORDER_CHANGE=true
```

1. **保存実行:**
    - 「新しいバージョンを追加」ボタンを押下して保存します。保存完了後、新バージョンが「有効（Enabled）」となります。

⚠️ **運用の極めて重要な注意点（Secret同期リスク）：** Secret Manager の新バージョンを追加したのみでは、**現在稼働中の Cloud Run コンテナやクライアント側に配信済みの動的バンドルには設定変更が一切反映されません**。 Secret の値をプログラムに読み込ませるためには、後述する **Cloud Build トリガーの手動再実行（Re-trigger）**、または **GitHub リリースPR（**`develop` **→** `main`**/**`master`**）のマージ** を実行し、新規シークレットを注入した状態での再ビルド・再デプロイが必須となります。

### 変更反映のためのビルド再実行連携

シークレット更新後、アプリケーションへ新設定を注入・反映させるため、以下のいずれかの手順でビルドをキックします。

- **GitHub PRマージ連携:** GitHub 上で `develop` から `main`/`master` へのリリースPRをマージし、関連する Cloud Build トリガーを自動発火させます。
- **Cloud Build 手動キック:** 既にコードがマージ済みの場合、または設定値のみを再注入して再構築したい場合は、Cloud Build 画面から対象トリガー（例: `careflow-web-production`）の「実行（Run）」ボタンを手動で押下します。
    - cloud build - トリガー - 一覧から実行

次セクションでは、ビルドが完了したアプリケーションをゼロダウンタイムで切り替える Cloud Run のトラフィック制御手順を解説します。

## 4. Cloud Run リビジョン管理と本番トラフィック切替手順

複数のマイクロサービスが相互に連携するシステムにおいて、APIとフロントエンド間の契約（データ構造やエンドポイント）の不一致によるエラーを防ぐため、Cloud Run のリビジョン管理を用いた厳格な順序でのトラフィック切り替えが必要です。

### 対象サービスの識別と厳密な切替順序の評価

手動でトラフィック切り替え操作を行う本番サービス群は、すべて **GCPプロジェクト:** `Analytics` に存在します。対象となる3つの本番サービスは以下の通りです。

1. `follow-crm-api-prod`（本番バックエンドAPI）
2. `follow-crm-api-worker-prod`（本番バックグラウンドワーカー）
3. `follow-crm-spa-prod`（本番フロントエンド SPA）

**切替順序の決定とその理由:** サービス間のバージョン不一致による画面エラーやリクエスト失敗を防ぐため、切り替えは以下の **絶対順序** で、タイムラグを最小限に抑えて連続実行します。

1. **第1順位：**`follow-crm-api-prod`
2. **第2順位：**`follow-crm-api-worker-prod`
3. **第3順位：**`follow-crm-spa-prod`
- **設定根拠:** フロントエンド（SPA）をバックエンド（API/Worker）より先に切り替えた場合、新しいSPAが未定義のAPIエンドポイントや変更されたレスポンス形式にリクエストを送信し、本番環境で障害が発生するリスクがあります。必ずAPIとWorkerのバックエンド層を先行して最新化し、新スキーマを受け入れ可能な状態にしてからSPAフロントエンドを切り替えます。

### トラフィック100%切り替えの標準ステップ

1. **GCPプロジェクトの確認とサービス選択:**
    - GCP Console のプロジェクトセレクターで `Analytics` プロジェクトを選択します。
    - 「Cloud Run」->「サービス（Services）」一覧画面を開き、対象サービス（例: `follow-crm-api-prod`）をクリックします。
2. **最新リビジョンの確認:**
    - 「変更履歴（Revision History）」タブを選択します。
    - ビルド完了によって新しく作成された最新リビジョン番号を確認します（例: APIにおいて旧 `335` から新 `336` へ、Workerにおいて旧 `321` から新 `322` へ更新されていることを確認）。
3. **トラフィック管理画面の起動:**
    - 画面上部の「トラフィック管理（Manage Traffic）」ボタンを押下します。
4. **100%割り当てと保存:**
    - 「すべてのトラフィックを1つのリビジョンに送信」を選択します。
    - 割り当て先リビジョンとして確認した最新リビジョン番号を指定し、トラフィック割合を 100% に設定して「保存」をクリックします。
5. **反映確認:**
    - 保存後、数十秒〜1分程度で本番トラフィックが最新リビジョンへ完全に切り替わります。

### マルチサービス切替チェックリスト

以下の順序に従い、3つの本番サービスの切替作業を漏れなく実施してください。

| 切替順序 | 対象GCPプロジェクト | サービス名 | 実施操作 | リビジョン移行例 | 反映時間目安 | 完了確認 |
| --- | --- | --- | --- | --- | --- | --- |
| **1** | `Analytics` | `follow-crm-api-prod` | トラフィック100%切替 | リビジョン 335 → **336** | 数秒〜1分 | [ ] |
| **2** | `Analytics` | `follow-crm-api-worker-prod` | トラフィック100%切替 | リビジョン 321 → **322** | 数秒〜1分 | [ ] |
| **3** | `Analytics` | `follow-crm-spa-prod` | トラフィック100%切替 | 旧リビジョン → **最新リビジョン** | 数秒〜1分 | [ ] |

次セクションでは、トラフィック切り替え直後に本番環境の健全性を確認するスモークテストおよび緊急切り戻し手順について説明します。

## 5. 本番環境デプロイ後検証（スモークテスト）および障害時切り戻し手順

トラフィック切替直後に実施するデプロイ後検証（スモークテスト）は、不具合によるエンドユーザー体験の損害やデータ整合性の破綻を防ぐための最終防波堤です。

### 本番検証（スモークテスト）の具体的確認項目

トラフィック切替完了後、直ちに以下の確認作業を実行してください。

1. **Web UI 基本疎通確認:**
    - Follow CRM 本番環境（`follow-crm-spa-prod`）にアクセスし、正常にログイン画面およびメインダッシュボードが表示されることを確認します。
2. **局所検証1：最適化レポート画面の表示検証:**
    - 今回のリリースに含まれるレポート表示項目の削減・最適化ロジックについて、該当レポート画面（ナビゲーション/ダイジェスト項目等）を開き、JavaScriptエラーや画面崩れが発生せず、不要項目が正常に除外されて高速表示されることを確認します。
3. **局所検証2：フィーチャーフラグ解放機能の動作検証:**
    - 患者詳細・医療機関詳細画面へ移動します。
    - 今回シークレット更新により有効化した **医療機関・紹介元一覧のドラッグ＆ドロップ機能** を操作し、表示順序の並び替えがスムーズに行えることを確認します。
    - 入院調整に関する画面要素が正常に表示され、機能することを確認します。

### 異常検知時のロールバック手順（即時一次対応）

スモークテスト中にUI崩れ、系統的なAPI通信エラー、または予期せぬスクリプトエラーが検知された場合は、開発チームの調査を待たず、直ちに以下の手順で旧バージョンへロールバックします。

1. **対象 Cloud Run サービスへ移動:**
    - GCP Console の `Analytics` プロジェクトにて、不具合が発生した対象サービス（`follow-crm-api-prod`、`follow-crm-spa-prod` 等）の画面を開きます。
2. **トラフィック管理の起動:**
    - 画面上部の「トラフィック管理（Manage Traffic）」を押下します。
3. **前回正常リビジョンへの100%割り当て:**
    - 切替直前に正常稼働していた旧リビジョン（例: API であれば `335`、Worker であれば `321`）を選択し、トラフィックを 100% に再設定して保存します。
4. **復旧確認:**
    - 保存後数十秒で旧バージョンへ復元されるため、本番画面でエラーが解消されたことを確認し、Slack等の関係者チャネルでロールバック実施を報告します。

次セクションでは、トラブル発生時のエスカレーションフローと、本作業手順の完了定義についてまとめます。

## 6. 運用エスカレーションフローと異常系トラブル対応マトリクス

デプロイ作業中に予期せぬビルド停止や環境間の非互換が発生した際に、迅速かつ的確に意思決定を行いチームへ共有するためのエスカレーション体制とトラブル対応表を以下に示します。

### トラブル対応マトリクス

| 障害・異常パターン | 対象GCPプロジェクト | 推定原因 | 一次対処手順 | 連絡ルート / エスカレーション先 |
| --- | --- | --- | --- | --- |
| **Cloud Build で** `Generating static pages` **時に約58分ハング・停止する** | `Analytics`<br>`medup-flow-prod` | Next.js静的ページ生成時の処理詰まり・ビルド環境依存 | 対象トリガーを手動再実行（Re-trigger）。再現する場合は本日の作業を中断し、本番トラフィック切替を行わずに調査依頼。 | 開発チーム / インフラリード |
| **Secret Manager 設定変更後、アプリに機能が反映されない** | `medup-flow-prod`<br>`Analytics` | シークレット更新後の Cloud Build 再実行（コンテナ再構築）漏れ | Secret Manager で新バージョンが正しく「有効」化されているか確認し、Cloud Build の対象トリガーを手動実行またはPRマージを実施。 | インフラ運用担当 / 開発チーム |
| **SPAまたはAPIで通信エラー・挙動不整合が発生** | `Analytics` | API / Worker / SPA 間の Cloud Run 切替順序の誤りまたはタイミングのズレ | 切替順序（API → Worker → SPA）を遵守し、`Analytics` プロジェクト内の3サービス全てのトラフィックを最新リビジョンへ一括100%割り当て。 | 運用担当者 / 開発チーム |
| **スモークテストにて本番UI崩れやJSエラーが発覚** | `Analytics` | デプロイコードの不具合または環境変数依存エラー | Cloud Run の「トラフィック管理」より、即座に前回の正常稼働リビジョン（API: 335, Worker: 321等）へ100%ロールバックを実施。 | 開発チーム / システム責任者 |

### 結論・完了定義

本作業手順書に従った一連のリリース作業は、以下のすべての条件が満たされた時点で「正常完了」と定義します。

1. **全対象 Cloud Run サービスのリビジョン同期完了:**
    - `Analytics` プロジェクトにおける `follow-crm-api-prod`、`follow-crm-api-worker-prod`、`follow-crm-spa-prod` の全3サービスにおいて、最新リビジョンへのトラフィック100%割り当てが完了していること。
2. **本番スモークテストの完全成功:**
    - Web UI 疎通、レポート画面表示、およびフィーチャーフラグ解放機能（医療機関・紹介元のドラッグ＆ドロップ並び替え等）がエラーなく正常動作することを確認済みであること。
3. **運用リリース完了報告の実施:**
    - 指定のSlack連絡チャネル（例: `#dev-release` 等）において、全リビジョン番号およびスモークテスト成功の旨を記載したリリース完了報告を送信していること。
